# ProSourcing 辅助编程核心军规 (Post-Mortem 2026-03-24)

> **目的**：杜绝回归漏洞、部署冲突与数据库同步遗漏。

## 1. 代码变更检查点：严禁盲目回退功能
- **失误复盘**：今日在更新需求时过快使用 `checkout`，由于未进行详细的 `diff` 或 `view` 确认，导致之前已实现的“详情页过滤”功能被意外删除。
- **强制规则**：
    1. 在任何 `checkout` 或大篇幅代码替换前，**必须先执行 `view_file` 确认当前的热代码逻辑**。
    2. 如果需要恢复历史版本，必须手动将热功能代码（如 `onlyHighQuality`）合并至目标文件。
    3. 操作后需使用 `grep_search` 搜索最近实现的关键逻辑词，验证是否依然存在。

## 2. 部署打包检查点：镜像版本号与路径完全对齐
- **失误复盘**：镜像打包时忽略了 `docker-compose.yml` 中的指定标签（`v20260324_clean`），且导出的 `.tar` 文件名与路径自定义化，导致用户无法直接部署。
- **强制规则**：
    1. 打包前**必读 `docker-compose.yml`**，确认各服务的 `image` 标签版本。
    2. 检查 `deployment_package` 目录结构，确保导出的 `.tar` 命名（如 `prosourcing-backend_v20260324_clean.tar`）与既有规范 100% 吻合。
    3. 严禁生产环境使用 `latest` 等不确定性标签。

## 3. 分支管理与 PR 制度：严禁直接推送到主分支
- **原则**：`main` 分支仅用于存放经过验证的生产版本。所有开发、修复任务必须在特性分支（Feature Branch）进行，并通过 PR 流程合并。
- **操作逻辑**：
    1. 任何新任务开始，必须先拉取最新主代并创建新分支：`git checkout -b feat/task-name`。
    2. 开发完成后，通过 `gh pr create` 或 Web 端发起合并请求。
    3. 合并前必须进行代码自检（Code Review），确认无功能回归（参考军规第 1 点）。
    4. 提交 Message 必须规范：`feat:` (新功能), `fix:` (修 Bug), `chore:` (常规维护)。

## 5. AI 开发规范：新需求自动“开辟战场”
- **强制触发**：当用户提出新需求或修复任务时，AI **必须主动**执行以下操作：
    1. **检查状态**：执行 `git status` 和 `git branch` 确认当前环境。
    2. **同步基准**：切回 `main` 分支并执行 `git pull origin main` 确保基础代码最新。
    3. **自动分支**：根据任务内容自动创建特性分支，命名规范为 `feat/xxx` 或 `fix/xxx`。
    4. **即时告知**：在回复中告知用户：“**哥，我已为您开辟新战场：`feat/xxx`，现在开始干活！**”
- **严禁**：严禁在未告知用户的情况下直接在 `main` 或旧的特性分支上堆叠不相关的改动。

## 4. RPA 性能与稳定规范
- **图片并行下载**：必须使用 `ThreadPoolExecutor`。
- **资源启动锁**：共用 Chrome 环境需加 `asyncio.Lock`。
