# Docker 现场环境 ORM 与事务治理方案

## 目标

本方案面向 Docker 现场部署环境，回答四个问题：

1. 当前是否值得引入 ORM
2. 哪些模块适合优先纳入 ORM 与事务治理
3. 哪些流程必须先补事务边界，暂时不必急着 ORM 化
4. 现场环境下事务回滚、失败补偿、备份恢复应如何分层处理

本方案以“低风险分阶段落地”为原则，不建议一次性全量重构。

## 当前现状梳理

### 1. 生产态数据访问存在双轨

当前主链路主要通过两种方式访问数据库：

- `core/final_pipeline.py`
  使用 `PGSupabaseShim` 模拟 Supabase 查询语法，在生产环境转到 PostgreSQL
- `core/rpa_final_pipeline.py`
  在生产环境直接使用 `psycopg2` 和手写 SQL

这带来几个直接问题：

- SQL 和数据访问规则分散在多个文件
- 同一张表在不同模块里可能有不同写法
- 事务边界依赖开发者手工控制，缺乏统一约束
- 出错时更容易出现“部分表写成功，部分表未写入”的状态

### 2. 已存在 ORM 试点痕迹，但未闭环

仓库中已有 ORM 方向的测试文件：

- `tests/test_orm_base.py`
- `tests/test_orm_minimal.py`

这些测试引用了 `core.db`、`core.models`，但当前主干中并未看到对应实现完整落地，说明：

- 团队已经判断 ORM 方向有价值
- 但主线仍未形成稳定、可复用的数据访问基座

这不是“是否从零开始评估 ORM”的问题，而是“如何把已验证方向收敛为可运维方案”的问题。

### 3. 当前高风险流程集中在多表写入链路

尤其需要优先治理的是以下流程：

- 采集任务创建与状态变更
- 原始商品数据写入 `products_raw_data`
- 计算结果写入 `products_calculated_metrics`
- 任务汇总字段更新 `analysis_tasks`
- 类目统计、回填和修复脚本

这些流程一旦中途失败，现场最怕的不是单条报错，而是：

- 任务状态显示完成，但数据并未写全
- 原始数据和计算结果不一致
- 修复脚本更新部分成功，无法快速追溯未完成范围

## 是否值得引入 ORM

结论：值得，但不建议全量替换现有 SQL。

### 推荐结论

- 引入 SQLAlchemy 2.x ORM 或 SQLModel 作为统一模型层和值对象层
- 保留部分高性能、批量导入场景的手写 SQL
- 优先统一事务管理，而不是先追求“所有 SQL 全部 ORM 化”

### 原因

ORM 的核心收益在这个项目里主要不是“少写 SQL”，而是：

- 统一表模型和字段定义
- 明确 session 生命周期
- 给事务、回滚、异常传播提供统一承载层
- 为后续 Alembic、审计字段、仓储层封装提供基础

如果只上 ORM、不治理事务，收益会很有限。反过来，即使有些批量 SQL 暂时不改 ORM，只要被纳入统一事务控制，稳定性也能明显提升。

## 推荐架构

### 1. 统一数据库基础层

新增统一数据库模块，至少包含：

- `engine`
- `SessionLocal` / `AsyncSessionLocal`
- 基础 `Base`
- 环境分流配置
- 事务上下文工具

建议原则：

- API 层和业务层不直接创建裸连接
- 禁止在业务函数内部随意 `commit`
- 统一由 service / unit-of-work 层管理提交与回滚

### 2. 分层建议

- ORM 模型层：承载核心业务表结构
- Repository 层：封装常用查询与写入
- Service 层：组织跨表事务
- Script 层：调用 service，不直接散写 SQL

这样做的目标不是“抽象得很漂亮”，而是保证：

- 事务边界只有少量入口
- 脚本和 API 不会各自实现一套写库逻辑

## 哪些模块优先纳入 ORM

### 第一优先级：任务主链路

建议优先纳入 ORM 的表：

- `analysis_tasks`
- `products_raw_data`
- `products_calculated_metrics`
- `category_last_crawl_dates`

原因：

- 这些表直接决定任务是否闭环
- 它们跨表写入频繁
- 一旦部分提交，现场定位成本最高

### 第二优先级：类目主数据与统计表

- `algatop_categories_master`
- `algatop_top_category_stats`

原因：

- 这些表更新频率低于任务主链路
- 但对前端显示和回补脚本影响大
- 适合在主链路稳定后纳入统一模型管理

### 第三优先级：低频管理类表

- 系统设置类表
- 用户/权限类表
- 日志索引类表

这部分可以后置，不应阻塞主业务事务治理。

## 哪些场景暂时保留手写 SQL

以下场景可以暂时保留 SQL 或 `execute_values`：

- 大批量导入
- 批量 upsert
- 数据修复脚本中的大范围批处理
- 明显依赖 PostgreSQL 特性的 SQL

但要满足两个前提：

1. 这些 SQL 仍然运行在统一 session / connection 管理下
2. 由 service 层定义提交、回滚和日志语义

换句话说，可以先不“ORM 化”，但不能继续“到处裸写库”。

## 事务与回滚策略

## 1. 事务回滚

事务回滚只解决“尚未提交”的写入失败问题。

必须纳入单事务的典型流程：

- 创建任务记录
- 写入商品原始数据
- 写入计算结果
- 更新任务状态和任务统计

建议规则：

- 成功则统一 `commit`
- 任一环节失败则统一 `rollback`
- 回滚后任务状态要明确标记为 `failed` 或 `retrying`
- 记录失败阶段、异常摘要、影响 task id

## 2. 失败补偿

对于已经提交成功但业务状态不完整的情况，不能依赖数据库事务，需要补偿机制。

建议引入：

- 幂等的修复脚本
- 可重试的任务恢复脚本
- 任务阶段状态字段，例如 `created`, `scraped`, `scored`, `exported`, `synced`

适用场景：

- Excel 导出成功但任务状态未回写
- 原始数据已写入，但统计字段未更新
- 某张汇总表回写失败，需要后补

## 3. 备份与恢复

备份恢复不是事务回滚的替代物，而是更高层的容灾能力。

Docker 现场建议：

- PostgreSQL 数据卷定期备份
- 关键表支持逻辑导出
- 修复脚本执行前做快照或导出
- 发布前保留一个最近稳定版本的镜像与 SQL 升级脚本

建议最小化要求：

- 每次结构变更前备份数据库
- 每次大批量修复前备份目标表
- 修复脚本必须输出影响行数与回滚参考条件

## 日志与可观测性要求

事务治理必须配合日志，否则现场问题仍然难查。

建议所有关键写入链路统一输出：

- task id
- category id
- 当前执行阶段
- 插入/更新行数
- 是否提交成功
- 是否发生回滚
- 补偿脚本执行摘要

推荐做法：

- API 层记录请求级日志
- Service 层记录事务阶段日志
- 脚本层输出结构化摘要

## Alembic 是否值得引入

结论：值得，但放在 ORM 基础层稳定之后。

建议顺序：

1. 先统一 engine/session/model 组织方式
2. 再引入 Alembic 管理 schema 演进

原因：

- 如果模型层还未稳定，先上 Alembic 只会增加维护噪音
- 一旦核心表进入 ORM 管理，Alembic 才能真正减少现场变更风险

## 分阶段实施计划

### 阶段 0：现状收口

- 明确当前生产写库入口文件
- 列出核心业务表和写入关系
- 清理或标注失效的 ORM 试点文件

交付物：

- 本方案文档
- 当前写库链路清单

### 阶段 1：先补事务，不急着全量 ORM

- 抽出统一数据库连接与事务上下文
- 把任务主链路改造成单事务提交
- 统一失败状态和异常日志

交付物：

- `db/session` 基础模块
- 任务主链路事务封装
- 失败回滚与日志规范

### 阶段 2：核心表 ORM 化

- 为 `analysis_tasks`
- `products_raw_data`
- `products_calculated_metrics`
- `category_last_crawl_dates`
  建立模型与 repository

交付物：

- 核心模型
- repository/service 封装
- 旧写法到新写法的迁移清单

### 阶段 3：修复脚本治理

- 回补脚本改为统一事务入口
- 为批量修复脚本增加 dry-run
- 输出影响范围和结果摘要

交付物：

- 幂等修复脚本模板
- dry-run 规范
- 执行日志模板

### 阶段 4：Schema 演进与现场运维

- 引入 Alembic
- 建立发布前备份清单
- 建立结构变更 SOP

交付物：

- 迁移脚本管理流程
- 结构升级/回退 SOP

## 不建议做的事

- 不建议一次性把所有 Supabase 风格调用改写成 ORM
- 不建议先大规模重构，再补事务
- 不建议让 API、脚本、pipeline 各自维护独立 session 管理方式
- 不建议把“事务回滚”和“数据补偿”混为一谈

## 最终建议

这个项目应该引入 ORM，但切入点应当是“统一事务与数据访问基座”，而不是“追求 ORM 覆盖率”。

最稳妥的路线是：

1. 先统一 session 和事务入口
2. 再把任务主链路核心表纳入 ORM
3. 批量导入和高性能修复脚本暂时保留 SQL
4. 最后再引入 Alembic 和更完整的模型治理

这样能在不激进重构的前提下，优先降低 Docker 现场运行中最昂贵的故障风险。
